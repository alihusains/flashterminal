# FlashTerminal Phase 3A

## Multi-Agent Task Engine + Deterministic Orchestration Foundation

FlashTerminal Phase 3A is now verified end-to-end.

Current release state:

```text
terminal-session 59/59 unit tests PASS
terminal-workspace suites PASS (incl. 18/18 Phase 3A: serial/parallel,
  retry, cancel, review boundary, budgets, determinism ×10, persistence
  restore, 100-task stress at max_agents 2/5/10, idle perf regression)
IPC task surface round-trip tests PASS
CLI end-to-end smoke: task create/list/run/cancel/retry/policy/scheduler PASS
clippy -D warnings PASS
fmt PASS
desktop build PASS (task dashboard + palette + Ctrl-Alt bindings)
release build PASS
```

The validated architecture currently is:

```text
Workspace
   ↓
Pane
   ↓
ExecutionId
   ↓
ExecutionKind
   ├── TerminalSession
   └── AgentSession
         ↓
      AgentRuntime
         ↓
      AgentAdapter
         ↓
   Claude / Codex / OpenCode / Pi
```

Phase 3 adds deterministic multi-agent orchestration:

```text
TaskGraph (insertion order, explicit transitions)
   ↓
TaskScheduler (step() = observe → classify → capacity arc)
   ↓
AgentRuntime (every spawn through adapters — never a raw subprocess)
   ↓
TaskEvent stream over the existing IPC bus
```

This is the first phase where multiple agents become a coordinated system.

---

# 1. Primary Objective

Build the foundational orchestration engine that allows FlashTerminal to represent and execute:

```text
Task
 ├── dependencies
 ├── assigned agent
 ├── execution
 ├── inputs
 ├── outputs
 ├── artifacts
 ├── status
 └── result
```

The core principle is:

> **Orchestration must be deterministic before it becomes autonomous.**

Do not build an LLM planner in this phase.

Do not build automatic agent routing.

Do not build agent teams UI.

Do not build a visual workflow editor.

First create a robust task engine.

---

# 2. Core Product Goal

The user should eventually be able to say:

```text
Build authentication for this project.
```

and FlashTerminal should be able to represent the work as:

```text
Authentication
│
├── Inspect repository
├── Design solution
├── Implement
├── Test
└── Review
```

However, Phase 3A must use an explicit task graph.

The graph may initially be created by:

* CLI
* structured API
* deterministic test fixture

An LLM planner comes later.

---

# 3. Introduce Task

Create:

```text
Task
```

Conceptually:

```rust
Task {
    id,
    title,
    description,
    status,
    dependencies,
    assigned_agent,
    execution_id,
    workspace_id,
    input_artifacts,
    output_artifacts,
    created_at,
    started_at,
    completed_at,
    error,
}
```

Keep Task separate from AgentSession.

---

# 4. Task vs AgentWork vs AgentSession

These three concepts must remain distinct.

```text
AgentSession
= running process/session

AgentWork
= work performed by one agent session

Task
= unit of work in an orchestration plan
```

Example:

```text
Task:
Implement Google OAuth

AgentWork:
Codex implementing OAuth

AgentSession:
codex process running in pane
```

Do not merge these concepts.

---

# 5. TaskStatus

Define:

```text
Pending
Ready
Running
Blocked
Waiting
NeedsReview
Completed
Failed
Cancelled
Skipped
```

Tasks should move through explicit state transitions.

Do not allow arbitrary state mutations.

Create a state transition function and test invalid transitions.

---

# 6. Task Graph

Create:

```text
TaskGraph
```

The graph should support:

```text
add_task
remove_task
add_dependency
remove_dependency
get_task
list_tasks
ready_tasks
validate
```

Represent dependencies as directed edges.

Example:

```text
Research
   ↓
Implementation
   ↓
Tests
   ↓
Review
```

---

# 7. Cycle Detection

Task graphs must reject cycles.

This must fail:

```text
A → B
B → C
C → A
```

Create deterministic tests for:

```text
simple cycle
long cycle
self dependency
duplicate dependency
missing dependency
```

The system must reject invalid graphs before execution.

---

# 8. Graph Validation

`TaskGraph::validate()` should check:

```text
unique task IDs
valid dependencies
no self references
no cycles
valid agent references
valid workspace
valid artifact references
```

Return structured errors.

Do not return generic string errors where a typed error is appropriate.

---

# 9. Task Dependencies

A task is:

```text
Ready
```

only when all dependencies are:

```text
Completed
```

For example:

```text
Research = Completed
Implementation = Ready
```

If:

```text
Research = Failed
```

then dependent tasks must not silently start.

Define explicit behavior:

```text
Blocked
```

or:

```text
Skipped
```

based on orchestration policy.

---

# 10. Scheduler

Create:

```text
TaskScheduler
```

Responsibilities:

```text
identify ready tasks
respect dependencies
assign work
start execution
monitor execution
process completion
handle failure
release dependent tasks
```

The scheduler must be deterministic.

Same graph + same initial state should produce the same schedule under the same configuration.

---

# 11. Scheduler Policies

Phase 3A should support only simple policies.

### Serial

One task at a time.

### Parallel

Run all currently ready tasks subject to concurrency limit.

### Fixed Agent Assignment

Each task specifies its agent.

Example:

```text
Research → Claude
Implementation → Codex
Tests → Pi
Review → OpenCode
```

Do not implement automatic agent selection yet.

---

# 12. Concurrency Limits

Create workspace-level orchestration limits:

```yaml
max_agents: 5
max_parallel_tasks: 5
```

The scheduler must never exceed the configured limit.

Eventually this can become dynamic.

---

# 13. Agent Assignment

A Task may specify:

```text
agent_definition_id
```

or:

```text
agent_execution_id
```

Define the difference carefully.

Prefer assignment to an AgentDefinition initially.

The scheduler creates an AgentSession when the task starts.

---

# 14. Task Execution

When a Task becomes ready:

```text
Task
 ↓
Scheduler
 ↓
AgentRuntime
 ↓
AgentSession
 ↓
Pane
```

The scheduler must NOT directly spawn processes.

It should call the existing AgentRuntime.

This preserves the architecture.

---

Failure:

# 19. Shared Context

```text

    dependencies
    artifacts
    relevant_files
```

The scheduler provides context to the AgentRuntime.

Do not implement an LLM context summarizer yet.

# 20. Agent Prompt / Instruction Boundary

Do not allow the scheduler to construct vendor-specific prompts.

Instead:

```text
Task
 ↓

 ↓
agent-specific execution
```

This keeps vendor-specific behavior inside the adapter layer.

---

# 21. Task Event Model

Create:

```text
TaskEvent
```

Examples:

```text
TaskCreated
TaskReady
TaskStarted
TaskBlocked
TaskWaiting
TaskNeedsReview
TaskCompleted
TaskFailed
TaskCancelled

```

Integrate it into the existing `ApplicationEvent`.

Do not create a completely separate event bus.

---

# 22. Event Ordering

Guarantee ordering for events belonging to the same Task.

For example:

```text
TaskStarted
TaskArtifactCreated
TaskCompleted
```

must not be delivered as:

```text
TaskCompleted
TaskStarted
```

Global ordering across unrelated tasks is not necessarily required.

Document the guarantees.

---

# 23. Persistence

Persist the task graph.

Use a versioned schema.

Persist:

```text
task IDs
graph edges
task state
agent definition references
artifacts
workspace
timestamps
results
```

Never persist:

```text
API keys
secret contents
raw credentials
```

---

# 24. Resume After Application Restart

On restart:

```text
TaskGraph
 ↓
restore
 ↓
inspect task states
```

Tasks in:

```text
Completed
Failed
Cancelled
```

remain unchanged.

Tasks in:

```text
Running
Waiting
```

must be treated as interrupted unless the underlying AgentRuntime supports safe restoration.

Do not pretend an arbitrary agent process continued while the application was offline.

Use:

```text
Interrupted
```

or:

```text
NeedsRecovery
```

where appropriate.

---

# 25. Failure Policies

The scheduler must support explicit policies.

### Fail Fast

One failed dependency blocks downstream work.

### Continue Independent Tasks

Unrelated tasks continue.

### Retry

Retry a failed task up to N times.

Example:

```yaml
max_retries: 2
```

Do not retry blindly.

Define which failures are retryable.

---

# 26. Retry Classification

Create:

```text
RetryPolicy
```

Potential categories:

```text
TransientProviderFailure
NetworkFailure
AgentCrash
AuthenticationFailure
TaskFailure
PermissionFailure
Unknown
```

Not every error should be retried.

Authentication errors should generally require user intervention.

---

# 27. Cancellation

Implement:

```text
cancel_task(task_id)
```

If a task is running:

```text
TaskScheduler
 ↓
AgentRuntime.stop(execution_id)
```

Then transition:

```text
Running
 ↓
Cancelled
```

Do not terminate the process directly from the scheduler.

---

# 28. Pause / Resume

Phase 3A does not need true task pause semantics.

Do not fake them.

If an agent supports pause, it may eventually be used.

Otherwise:

```text
pause task
```

should remain unsupported or represent a scheduler-level pause before execution.
