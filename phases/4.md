FlashTerminal has completed the major terminal, workspace, agent and orchestration architecture.

Current state:

```text

✅ Phase 3E
✅ Phase 3F
```

Phase 3F completed:

```text
28/28 Phase 3F tests passing
cargo test --workspace: clean
```

During Phase 3F, two genuine engine bugs were found and fixed:

1. `PAUSE-ALL` phantom-running state in orchestration.
2. Secret leakage through `export_persisted()`.

These fixes must remain covered by permanent regression tests.

The multiplexer benchmark previously exhibited a rare focused-shell wedge. The current harness has forensic diagnostics and 22 consecutive clean runs. Continue treating the underlying shell/TTY bimodality as a documented stress risk rather than assuming it can never recur.

# PHASE 4 OBJECTIVE

Do not add major new AI capabilities.

The objective is:

> Make FlashTerminal trustworthy enough for users to let multiple agents execute meaningful work without constantly babysitting them.

This phase is about:

```text
Security
Safety
Policy
Recovery
Auditability
Reliability
Performance
Distribution
Human control
```

# 1. Create a Central Policy Engine

Introduce a centralized policy layer.

Conceptually:

```text
User
  ↓
Policy Engine
  ↓
Planner
  ↓
Plan Validator
  ↓
Approval
  ↓
Execution
```

The planner must never be the final authority.

Create policy domains:

```text
Filesystem
Network
Process
Secrets
Shell
Workspace
Agent
Budget
Autonomy
```

---

# 2. Policy Evaluation

Every executable action should be evaluable against policy.

Conceptually:

```rust id="q2l3f9"
PolicyDecision {
    action,
    decision,
    risk,
    reasons,
    policy_source,
}
```

Possible decisions:

```text
Allow
Deny
RequireApproval
```

Never silently downgrade:

```text
Deny
```

to:

```text
Allow
```

---

# 3. Risk Classification

Create a normalized risk model:

```text
Low
Medium
High
Critical
```

Example:

```text
ls
→ Low

npm install
→ Medium

network request
→ Medium

rm -rf project
→ High

modify SSH credentials
→ Critical
```

Do not build a perfect command classifier.

Build a conservative extensible system.

When uncertain:

> require approval.

---

# 4. Dangerous Command Protection

Create deterministic protections against clearly dangerous operations.

Cover:

```text
rm
rmdir
sudo
chmod
chown
mkfs
dd
disk operations
system configuration
credential access
SSH key access
destructive Git commands
force push
mass deletion
```

Do not rely solely on an LLM classifier.

Use deterministic rules first.

---

# 5. Structured Process Execution

Where possible, execute commands using:

```text
executable
arguments[]
```

rather than:

```text
shell string
```

Avoid unnecessary shell interpolation.

Never concatenate untrusted agent/planner values into shell commands.


# 9. Worktree Isolation

Strengthen the existing worktree model.

Each autonomous agent should have:

```text
workflow_id
agent_id
worktree_path
allowed_paths
```

An agent must not write to another agent's worktree.

Test malicious path traversal and symlink scenarios.



# 14. Autonomy Levels

Create explicit autonomy modes:

```text
Manual
Assisted
Supervised
Autonomous
```

Define exactly what each mode allows.

Example:

### Manual

Every risky action requires approval.

### Assisted

Low-risk actions automatic.

### Supervised

Medium-risk actions automatic inside policy scope.

### Autonomous

High automation within a strict sandbox and budget.

Critical actions still require explicit user approval.

Do not equate:

> Autonomous

with:

> unrestricted.

# 16. Approval Changes


# 36. Multiplexer Benchmark Wedge

The Phase 3F stress benchmark previously exhibited a rare focused-shell wedge.

The current harness has:

```text
22 consecutive clean runs
```

Keep the forensic wedge dump.

Do NOT classify future occurrences as benchmark artifacts automatically.

If the wedge occurs again:

1. Capture the forensic dump.
2. Determine whether the focused shell exited.
3. Determine whether PTY bytes continue arriving.
4. Determine pending write length.
5. Determine reader progress.
6. Determine engine drain progress.
7. Classify the failure.

Only then decide whether it is:

```text
Fixture artifact
OS/TTY behavior
FlashTerminal bug
```

# FINAL PRINCIPLE

FlashTerminal should never optimize for:

> "The agent successfully did something."

It should optimize for:

> **"The agent successfully did something while the user remained in control, could understand what happened, could recover from failure, and could trust the system."**

Performance remains non-negotiable.

Human control remains non-negotiable.

Security remains non-negotiable.

Transparency remains non-negotiable.
