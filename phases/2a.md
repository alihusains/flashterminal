# FlashTerminal Phase 2A

## Execution Session + Agent Runtime Foundation

The repository has now been reconciled against the actual source tree.

Authoritative project state:

```text
✅ Phase 0
✅ Phase 0.5
✅ Phase 0.5.1
✅ Phase 0.5.2
✅ Phase 1
→ Phase 2A
```

Phase 1 is already implemented and MUST NOT be reimplemented.

The current workspace architecture already contains:

```text
Workspace
  ↓
Tab
  ↓
Pane
  ↓
SessionId / TerminalSession
```

The terminal core is validated and must remain stable.

This phase introduces the foundation for AI agents without yet implementing multi-agent orchestration.

---

# 1. Objective

Create a provider-neutral execution abstraction that allows a Pane to host different kinds of executable sessions.

The first supported execution types are:

```text
TerminalSession
AgentSession
```

The architecture must later be extensible to:

```text
RemoteSession
ContainerSession
LogSession
PreviewSession
```

without redesigning Workspace or Pane.

---

# 2. Important Architectural Rule

Do NOT make Pane depend directly on TerminalSession.

The desired conceptual architecture is:

```text id="m9u7gn"
Workspace
   ↓
Tab
   ↓
Pane
   ↓
Execution Handle
   ├── TerminalSession
   └── AgentSession
```

The Pane should know:

* execution/session identity
* pane type
* title
* geometry
* focus
* lifecycle state

The Pane should NOT know:

* PTY implementation
* VTE implementation
* Claude internals
* OpenAI internals
* model/provider internals

---

# 3. Do Not Build a Giant Trait

Do not immediately create one enormous:

```rust
trait ExecutionSession
```

containing every possible operation.

Instead separate common concerns from optional capabilities.

Define a minimal core identity/lifecycle model and capability-oriented interfaces.

Conceptually:

```text id="r1d8h0"
ExecutionHandle
    │
    ├── Lifecycle
    ├── Input
    ├── Output
    ├── Resize
    ├── Observable
    └── Persistence
```

Not every execution type must implement every capability.

For example:

```text
TerminalSession
  Lifecycle ✓
  Input ✓
  Output ✓
  Resize ✓
  Observable ✓

AgentSession
  Lifecycle ✓
  Input ✓
  Output ✓
  Resize ? 
  Observable ✓
```

Do not invent unsupported capabilities.

## Problem

Pane currently assumes a terminal session.

## Goal

Allow terminal and agent sessions to share workspace infrastructure.

## Options considered

At minimum:

1. giant trait
2. enum
3. capability-oriented composition
4. separate Pane types
5. generic session IDs

## Decision

Select the architecture based on:

* performance
* ownership
* extensibility
* serialization
* UI simplicity
* testing
* future agent compatibility

## Consequences

Document trade-offs.

# 6. Execution Identity

Create a stable execution/session identity.

Conceptually:

```rust
ExecutionId
```

Do not overload:

```text
SessionId
```

if it is currently terminal-specific.

The identity should be unique across:

```text
TerminalSession
AgentSession
```

and future session types.

---

# 7. Execution Kind

Create a lightweight discriminator:

```text
ExecutionKind
  Terminal
  Agent
```

Future possibilities can be added later.

Do not create implementations for future types yet.

---

# 8. Execution Metadata

Create something conceptually like:

```rust
ExecutionMetadata {
    id,
    kind,
    title,
    cwd,
    created_at,
    state,
}
```

Keep metadata lightweight.

Do not put the entire terminal state inside it.

Do not store secrets here.

---

# 9. Capability Model

Create explicit capability concepts.

Possible capabilities:

```text
CanInput
CanResize
CanOutput
CanObserve
CanPause
CanResume
CanStop
CanRestart
CanPersist
CanInteract
```

Do not use a giant boolean structure unless it is actually useful.

Prefer a type-safe representation where practical.

The important requirement is:

> UI and orchestration code should be able to discover what an execution supports without guessing.

# 19. Agent Adapter Interface

Design an adapter boundary similar to:

```text
AgentRuntime
      ↓
AgentAdapter
      ↓
External Agent
```

The adapter owns provider-specific behavior.

The workspace engine must NOT contain code such as:

```text
if agent == claude
if agent == codex
```

All vendor-specific logic must live in adapters.


# 28. Event Unification

Avoid creating an independent event architecture for agents.

Use an application-level event model conceptually like:

```text
ApplicationEvent
├── WorkspaceEvent
├── PaneEvent
├── TerminalEvent
├── AgentEvent
└── NotificationEvent
```

The exact implementation is your decision.

The objective is to avoid several unrelated event buses.

---

# 29. Persistence

Persist only what is appropriate:

```text
ExecutionId
ExecutionKind
AgentDefinitionId
pane association
cwd
metadata
last known state
```

Do NOT persist:

* API keys
* secrets
* raw credentials
* arbitrary live process state

Best-effort restoration is acceptable.

For agents that cannot be resumed:

```text
Agent session could not be restored.
```

Do not pretend otherwise.

# 31. Security Preparation

Do not implement full sandboxing yet.

But define an extensible permission model:

```text
AgentExecution
 └── PermissionPolicy
       ├── filesystem
       ├── network
       ├── process
       ├── environment
       └── secrets
```

The Agent Runtime must execute through a boundary where these policies can later be enforced.

Do not design the system so that permissions have to be retrofitted into every adapter.
