# FlashTerminal Phase 0.5.2

## Scrollback Scalability + Final Release Gate

Phase 0.5.1 found and fixed a genuine production PTY write deadlock.

The current automated results are strong:

```text
input p95 under load: ~1.89 ms
coalescing: 7.89M events → 22.4K batches → 5.26K renders
glyph cache hit rate: 100% on current workload
PTY backpressure test: PASS
```

However, stress testing revealed a scalability concern:

```text
10 heavy panes: ~597 MB RSS
20 heavy panes: ~1.16 GB RSS
```

The investigation indicates the dominant factor is the current in-memory scrollback representation.

This must be addressed before Phase 1.

Do NOT implement:

* multiplexer
* workspaces
* agents
* BYOK
* orchestration
* browser
* editor
* plugins

This phase is exclusively about making the existing terminal core scalable.

---

# 1. Primary Goal

Change the terminal history architecture so that memory usage remains bounded under sustained high-volume output.

The target is:

> Long-running terminal output should not cause RAM usage to grow linearly with the number of historical rows retained.

The terminal should be able to retain substantial history without keeping every historical cell in fully expanded hot RAM.

# 3. Define Scrollback Tiers

Design a tiered model.

Conceptually:

```text
Visible Screen
      │
      ▼
Hot Scrollback
      │
      ▼
Cold Scrollback
      │
      ▼
Optional Disk Storage
```

The exact implementation is an engineering decision.

Requirements:

### Visible Screen

Must remain extremely fast.

### Hot Scrollback

Keep a bounded amount in RAM for immediate scrolling.

### Cold Scrollback

Older terminal history should use a much more memory-efficient representation.

Possible approaches:

* compressed row representation
* compact cell encoding
* compressed blocks
* disk-backed blocks
* hybrid memory/disk

Do not choose an implementation merely because it is easy.

Benchmark candidates.

# 4. Memory Goals

Create explicit targets.

For a 120-column terminal:

```text
10,000 historical rows
```

should not automatically imply approximately:

```text
19 MB
```

of expanded cell memory per pane.

The long-term requirement is:

```text
memory usage plateaus as history grows
```

rather than:

```text
memory usage ∝ history length
```

# 11. Channel Capacity

Do NOT simply increase:

```text
1024
```

to:

```text
4096
```

without measurement.

First determine:

```text
PTY throughput
parser throughput
event queue throughput
state application throughput
render throughput
```

If the queue reaches capacity during heavy output, determine whether:

* event batching is insufficient
* state application is too slow
* renderer preparation is too slow
* terminal state mutation is too expensive

Then optimize the actual bottleneck.
