# FlashTerminal Phase 2C.1

## Full Verification, Failure Investigation and UI Release Gate

FlashTerminal Phase 2C has been substantially implemented according to `2c.md`.

However, the current implementation analysis is NOT sufficient to declare Phase 2C complete.

The analysis reports:

```text
terminal-core tests:
18/18 PASS

terminal-session tests:
7 PASS
4 FAIL
```

It also reports that several UI-facing capabilities exist in models/plumbing but still require actual desktop validation.

Therefore:

> **Do not declare Phase 2C complete yet.**
>
> Do not begin Phase 3.
>
> Do not add new major features.
>
> This phase is now a strict verification and release-gate phase.

The goal is to determine what is actually complete in the running product, fix genuine regressions, verify the UI, and produce an evidence-based final Phase 2C verdict.

---

# 1. Authoritative Rule

Do not consider a feature complete merely because:

* a struct exists
* an enum exists
* a helper function exists
* a command mapping exists
* a model serializes
* source inspection suggests it is implemented

A feature is complete only when:

```text
implementation
+
automated test
+
runtime integration
+
UI behavior where applicable
+
performance validation
```

are all verified.

Source inspection alone is not sufficient.

# 4. Investigate Every Failed Test

The current report mentions:

> `phase051.rs:519 top interactive round-trip`

and claims the failures are pre-existing PTY issues.

This assertion must be proven.

For each failed test determine:

```text
test name
failure point
stack trace
source file
whether Phase 2C changed any relevant code
whether the test fails on the current branch before Phase 2C changes
whether it fails deterministically
```

Run the failing test individually:

```bash
cargo test -p terminal-session <test-name> -- --nocapture
```

Then repeat it multiple times.

For timing-sensitive tests use:

```bash
cargo test -p terminal-session <test-name> -- --nocapture --test-threads=1
```

If a test passes and fails intermittently, classify it as:

```text
FLAKY
```

not:

```text
PRE-EXISTING
```

unless Git history proves that.

# 5. Determine Regression Status

For every failure answer:

```text
Was it introduced by Phase 2C?
Was it introduced earlier?
Is it an environment issue?
Is it a flaky test?
Is the test itself invalid?
```

If the test is genuinely invalid, fix the test.

If the implementation is wrong, fix the implementation.

Do not suppress failures simply to achieve green CI.
