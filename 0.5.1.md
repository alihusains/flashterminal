# 4. Threading and Ownership Audit

Determine exactly:

* which thread owns the PTY
* which thread reads PTY output
* which thread performs parsing
* which thread owns terminal state
* which thread handles UI input
* which thread owns wgpu resources
* which thread schedules rendering
* where mutexes exist
* where channels exist
* where shared mutable state exists

The desired model is:

```text
PTY
 ↓
IO Reader
 ↓
VT Parser
 ↓
Terminal Event
 ↓
Event Queue
 ↓
Terminal State Engine
```

There must be exactly one authoritative owner of mutable terminal state.

Do not allow multiple threads to independently mutate terminal state.

Prefer message passing / ownership transfer over shared mutable state.

Avoid unnecessary locks in the rendering path.

# 5. Introduce TerminalEvent

The VT parser should not directly become a renderer or UI abstraction.

Introduce a semantic event layer.

Create something conceptually like:

```rust
pub enum TerminalEvent {
    Print,
    CursorMove,
    CursorPosition,
    Erase,
    InsertLines,
    DeleteLines,
    Scroll,
    SetAttribute,
    SetForeground,
    SetBackground,
    Bell,
    Resize,
    TitleChange,
    ModeChange,
}
```

Adapt the exact API to the existing implementation.

The parser must translate terminal byte streams into semantic terminal events.

The Terminal State Engine applies those events.

# 7. Event Queue / Batching

Implement a bounded event ingestion mechanism.

Critical requirement:

> Renderer pressure must never prevent the PTY reader from draining process output.

Do NOT create this failure mode:

```text
PTY output
 ↓
channel full
 ↓
reader blocks
 ↓
PTY pipe fills
 ↓
child process blocks
 ↓
terminal appears frozen
```

The IO reader must continue draining the PTY.

Rendering may fall behind or coalesce updates, but terminal ingestion must not stall simply because the GPU is busy.

Design for:

```text
many PTY bytes
 ↓
parser
 ↓
event batches
 ↓
state engine
 ↓
coalesced render
```

---

# 8. Event Coalescing

Implement render coalescing.

For example:

100,000 lines of output must NOT cause:

```text
100,000 render requests
```

Instead:

```text
100,000 PTY operations
        ↓
state updated
        ↓
dirty regions accumulated
        ↓
one or a few render passes
```

The exact batching strategy is your engineering decision.

Benchmark it.

# 10. Render Snapshot Boundary

Do not let the renderer freely access mutable terminal state.

Introduce an explicit render boundary such as:

```text
TerminalState
      ↓
RenderSnapshot / render data
      ↓
Renderer
```

The render snapshot should contain only what the GPU renderer needs.

Potentially:

```text
visible cells
glyph IDs
colors
attributes
cursor
selection
dirty regions
```

Use an efficient mechanism appropriate to Rust and your threading model.

Possible approaches:

* immutable snapshots
* double-buffered render state
* versioned state
* command buffers
* changed-region updates

Choose based on benchmarks.

Document the decision.

# 13. Scrollback Separation

Separate visible terminal state from potentially large scrollback.

Conceptually:

```text
Terminal State
├── Visible Screen
├── Alternate Screen
├── Cursor
├── Selection
└── Modes

Scrollback
├── Hot Buffer
├── Compressed Chunks
└── Optional Disk Storage
```

Do not allow scrollback history to consume unbounded hot memory.

The renderer should primarily operate on the visible region.
