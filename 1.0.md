# FlashTerminal Phase 1

## Native Multiplexer + Workspace Engine

FlashTerminal Phase 0.5 and Phase 0.5.2 have established a validated high-performance terminal foundation.

Current verified architecture:

```text
PTY
 ↓
IO Reader
 ↓
VT Parser
 ↓
Terminal Events
 ↓
Bounded Event Queue
 ↓
Single-owner Terminal State Engine
 ↓
Render Snapshot
 ↓
Dirty-region rendering
 ↓
Glyph Cache
 ↓
GPU Glyph Atlas
 ↓
wgpu
```

The Phase 0.5.2 validation established:

```text
82/82 workspace tests passing
clippy: clean
fmt: clean
release build: passing

scrollback:
3.43 MB flat from 10k → 1M history rows

20-pane state plateau:
67.4 MB

input p95:
~1.31 ms

coalescing:
7.9M events → 4.7k renders

glyph cache:
100% hit rate on benchmark workload
```

A real PTY write deadlock and an O(n²) pending-write bug were discovered and fixed during validation.

The tiered scrollback architecture is now established.

---

# IMPORTANT

Before doing any Phase 1 implementation:

1. Read all Phase 0.5 and Phase 0.5.2 architecture documents.
2. Read the current `TerminalSession` API.
3. Read the scrollback ADR.
4. Read the performance report.
5. Inspect the current threading model.
6. Inspect existing benchmarks and tests.
7. Preserve the terminal-core architecture unless there is a demonstrated reason to change it.

Do NOT rewrite the terminal core.

Do NOT reimplement PTY handling.

Do NOT replace the scrollback model.

Do NOT introduce AI yet.

# 2. Phase 1 Primary Objective

Build a native multiplexer and workspace engine.

The user should be able to create:

```text
Workspace
    ├── Tab
    │    ├── Pane
    │    │    └── TerminalSession
    │    ├── Pane
    │    │    └── TerminalSession
    │    └── Pane
    │         └── TerminalSession
    │
    └── Tab
         └── Pane
              └── TerminalSession
```

The terminal session must remain independent of UI layout.

---

# 3. Architectural Rule

Do NOT put terminal state inside Pane.

Do NOT make the renderer own Pane state.

Do NOT make the workspace manager own terminal internals.

Use clear boundaries:

```text
Workspace
    owns Tabs

Tab
    owns Pane tree

Pane
    references TerminalSession

TerminalSession
    owns PTY + parser + terminal state

Renderer
    renders Pane snapshots
```

---

# 8. TerminalSession Boundary

Treat the existing `TerminalSession` as a reusable service.

A Pane should communicate with it through a well-defined API.

Example:

```text id="72q9pl"

 ↓
TerminalSession
 ↓
PTY / parser / state
```

Do not allow the Pane to access low-level PTY internals.

# 10. Render Routing

Rendering should follow:

```text id="eeuh3h"
Workspace
 ↓
Active Tab
 ↓
Visible Panes
 ↓
RenderSnapshot per TerminalSession
 ↓
Shared GPU Renderer
```

The renderer must NOT create an independent GPU context per pane.

Use a shared renderer wherever appropriate.

---

# 11. Shared Glyph Resources

The current glyph atlas architecture should be reused.

Do not create:

```text id="vz6a3v"
one glyph atlas per pane
```

Prefer:

```text id="kwxu7j"
Application Renderer
    ↓
Shared Font / Glyph Resources
    ↓
All panes
```

This is important for FlashTerminal's memory goals.


# 22. State Application Bottleneck

The Phase 0.5.2 report identified:

> State-application throughput is currently the pipeline bottleneck under heavy multi-pane saturation.

Do NOT ignore this.

Before implementing large-scale pane creation, instrument:

```text
PTY throughput
parser throughput
event queue depth
state application throughput
render preparation
GPU submission
```

Create a metric:

```text
state_events_per_second
```

and:

```text
state_apply_latency_p95
```

# 27. Fairness

The focused pane must receive priority.

Do not allow:

```text id="y6m4v3"

```

to starve:

```text id="40acgb"

```

Introduce scheduling priority where necessary.

Conceptually:

```text id="6u3cd7"
focused pane
    >
visible panes
    >
background panes
```

Do not starve background panes indefinitely.

# 28. Rendering Scheduling

A pane producing continuous output should not force the application into pathological frame rates.

Use the existing event coalescing strategy.

Across multiple panes:

```text id="h6hrpl"
Pane A events
Pane B events
Pane C events
      ↓
coalesced application render
      ↓
single frame
```

# 29. Memory Constraints

Preserve tiered scrollback.

Each terminal session should retain the bounded scrollback architecture.

The multiplexer must not accidentally duplicate scrollback memory.

Avoid:

```text id="9ibxy8"
TerminalSession
+ copied TerminalState
+ copied RenderSnapshot
+ copied scrollback
```

where possible.

Render snapshots should only hold the minimum necessary data.

# Final principle

FlashTerminal is not trying to reproduce tmux visually.

The goal is:

> **tmux-level composability without tmux-level cognitive overhead.**

A user should be able to manage dozens of terminals eventually without needing to think about pane IDs, sessions, PTYs, process IDs or multiplexing internals.

Keep all of that complexity underneath the workspace abstraction.

Do not start the agent layer until the workspace engine is stable and benchmarked.
