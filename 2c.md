# FlashTerminal Phase 2C

## Agent Experience + Observability + Intent Layer

FlashTerminal Phase 2B.1 is complete.

Current validated architecture:

```text id="z4n5ja"
Workspace
   ↓
Pane
   ↓
ExecutionId
   ↓
ExecutionKind
   ├── TerminalSession
   └── AgentSession
        ↓
     AgentRuntime
        ↓
     AgentAdapter
        ↓
    Claude / Codex / OpenCode / Pi
```

Phase 2B.1 has already implemented:

* real CLI agent execution
* Claude adapter
* Codex adapter
* OpenCode adapter
* Pi adapter
* Generic CLI adapter
* provider abstraction
* model abstraction
* Keychain BYOK
* secret redaction
* agent pane

* agent sidebar
* IPC event streaming
* agent concurrency testing
* real-agent validation

* security tests
* fake-agent infrastructure

Current release gates:

```text id="e20qjx"
163/163 workspace tests
clippy clean
fmt clean
release build clean
10-agent concurrency PASS
starvation PASS
memory PASS

```

Do NOT reimplement Phase 2A or Phase 2B.

Do NOT build multi-agent orchestration in this phase.

Do NOT build task graphs.

Do NOT build automatic agent routing.

Do NOT build agent teams.

Phase 2C exists to turn the current technically capable agent runtime into a **best-in-class human experience** and to establish the observability primitives required by Phase 3.

---

# 1. Product Objective

The user should be able to look at FlashTerminal and immediately answer:

```text id="9a12m6"
What are my agents doing?
Which ones are waiting?
Which ones need me?
What changed?
What failed?
What did they modify?
How much did this cost?
What should I do next?
```

without reading raw terminal output.

The raw terminal must remain available.

The default experience should communicate **work**, not logs.

---

# 2. Core UX Principle

The product must follow:

> **Show the work first. Keep the machinery available underneath.**

For example, instead of:

```text id="fdu4j1"
Claude
$ npm test
...
...
...
```

the default agent surface should communicate:

```text id="zv7w6n"
Claude Code

🟢 Working

Authentication

✓ Read 14 files
✓ Modified 8 files
✓ Added OAuth flow
→ Running integration tests
```

The raw terminal should be one click away.

# 3. Agent Work Model

Introduce an explicit concept of:

```text id="1sfvde"
AgentWork
```

This is not the same as `AgentSession`.

An `AgentSession` represents a process.

`AgentWork` represents what the agent is trying to accomplish.

Keep them separate.

Conceptually:

```text id="jjlgj2"
AgentWork
 ├── title
 ├── description
 ├── status
 ├── session_id
 ├── started_at
 ├── completed_at
 ├── files_changed
 ├── commands
 ├── activity
 ├── errors
 └── metrics
```

Do not implement multi-agent task graphs yet.

This is a single-agent work abstraction.

---

# 5. Activity Source

The current implementation already records:

```text id="q9j5r1"
state_source
state_confidence
```

Keep this.

Expand it into a consistent internal model:

```text id="fgykri"
ActivitySource
 ├── Structured
 ├── Hook
 ├── Protocol
 ├── Process
 └── Heuristic
```

The priority should be:

```text
Structured / Protocol
      ↓
Hook
      ↓
Process lifecycle
      ↓
Heuristic
```

Heuristics remain an important fallback.

Do not let heuristic detection become the primary architecture where structured mechanisms exist.

# 38. Natural Language Intent Layer

Create an abstraction for future intent commands.

Do NOT make an LLM mandatory.

The architecture should allow:

```text id="v5jhz1"
Intent
 ↓
Resolver
 ↓
Command
```

Example:

```text id="1iq0dg"
"show agents that need me"
```

may resolve deterministically to:

```text id="9mvnuz"
ShowAgents(NeedsAttention)
```

Later, an LLM can resolve more ambiguous requests.

Do not call an LLM for simple commands.
